# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

RedCheck is an interactive time/task management SPA that uses AI ("SmartCheck AI") to prioritize daily workloads (risk level, execution order, reasoning). This repo is the **frontend only** — the backend lives in a sibling repo at `../redcheck-backend` (not part of this working directory, but available locally for reference if API contract context is needed).

Write new code comments and commit messages in English, even though some existing code (e.g. `ThemeContext.tsx`) has Spanish comments/names.

Commits follow Conventional Commits style: `feat: ...`, `fix: ...`, `chore: ...`, `refactor: ...`, `docs: ...`, etc.

Automated tests use Vitest + React Testing Library (added 2026-09-09) — see the Testing section below. Coverage is intentionally a smoke-test layer (renders without crashing, key interactions), not exhaustive; don't assume every component has a test.

## Commands

```bash
npm run dev         # start Vite dev server
```

## Environment

- `VITE_API_URL` — base URL for the backend API, consumed by `src/api/axiosConfig.ts` at build time. Set via `.env` locally, or passed as a Docker build ARG in production (see `Dockerfile`).
- `VITE_GOOGLE_CLIENT_ID` — the Google OAuth Web Client ID used by `LoginPage.tsx`'s "Sign in with Google" button. Optional: when unset/empty, the entire Google section (divider + button) doesn't render at all (see "Sign in with Google" below), so a local/dev checkout with no Google Cloud project configured yet still works normally with password login.
- Production deploy is Docker + NGINX: Vite build output is served statically, and NGINX reverse-proxies API paths (`/auth`, `/users`, `/subjects`, `/tasks`, `/recurring_tasks`, `/recurring-tasks`, `/progress_records`, `/notifications`, `/ai`, etc.) to the backend container — `nginx.conf` is baked into the frontend's own Docker image (see `Dockerfile`) and ships through *this* repo's CI/CD, not `redcheck-infrastructure`'s (that repo's own `nginx/default.conf` just forwards all of `my.redcheckapp.com` to the frontend container; this file is what actually splits API traffic from the SPA). **A new top-level backend endpoint (not nested under an already-proxied prefix like `/subjects/{id}/...`) needs its own `location` line added here, or it 404s as HTML instead of hitting the backend** — the request still gets a `200`, since it silently falls through to the SPA's `try_files ... /index.html` catch-all instead of erroring, which makes the failure mode easy to miss without explicitly checking the response's `Content-Type` (fixed once already, 2026-09-09: `GET /recurring-tasks`, the global routines endpoint, was missing this and returned `index.html` in production until this file added a matching `location` block — `/recurring_tasks` here is unrelated legacy dead config, an old underscored path no current backend route uses).

## Architecture

**Layering:** the codebase strictly separates presentation from data access from global state:

- `src/api/` — one file per backend domain (`authApi.ts`, `taskApi.ts`, `subjectApi.ts`, `recurringTaskApi.ts`, `progressRecordApi.ts`, `smartCheckApi.ts`, `userApi.ts`, `registerApi.ts`), all built on a shared Axios instance in `axiosConfig.ts`. That instance auto-attaches `Authorization: Bearer <token>` from `localStorage` via a request interceptor — new API calls should go through this `api` instance rather than raw `axios`/`fetch`, and API functions should be fully typed against `src/types/index.ts`. A response interceptor there also clears the token and redirects to `/login` on a 401 for a request that carried a token (a plain failed-login 401, with no token yet, is left alone so the caller's own error message still shows).
- `src/context/` — global state via React Context, not a state library. `ThemeContext` and `LanguageContext` follow the same pattern: state is initialized with a priority chain (shared cookie → `localStorage` → system/browser preference) and persisted back to both a shared cookie and `localStorage` on change. If adding another cross-page persisted preference, follow this same cookie+localStorage dual-write pattern via `src/utils/cookies.ts` (`getSharedCookie`/`setSharedCookie`) rather than introducing a new mechanism.
- `src/pages/` — route-level components, wired up in `src/App.tsx` (`react-router-dom` `BrowserRouter`/`Routes`). Current routes: `/`, `/login`, `/register`, `/dashboard`, `/terms`, `/privacy`.
- `src/components/` — reusable, mostly presentational UI. Heavy use of `createPortal` for floating elements (modals, tooltips) to avoid `z-index` stacking issues — follow this pattern for new overlay/modal components rather than relying on z-index alone.
- `src/components/Sidebar.tsx` — the "Analyze Risks" button and the "SmartCheck AI / Analysis Engine" label are intentionally hidden (not deleted) behind `SHOW_RISK_ANALYSIS_BUTTON` / `SHOW_ANALYSIS_ENGINE_LABEL` flags at the top of the file, per a product decision to not expose them yet — flip the flag to `true` to bring one back rather than re-implementing it. The collapsed-sidebar sparkle icon (desktop only, `sm:` and up) is the intended replacement AI hint: visible while the sidebar is collapsed, fades out on expand, never rendered on mobile. The mobile drawer also supports swipe-to-close (drag left past ~30% of its width), implemented with raw `onTouchStart/Move/End` handlers rather than a gesture library — keep that pattern if extending the gesture.
- `src/types/index.ts` — single shared file for API request/response and domain types (`TaskResponse`, `SubjectResponse`, `RecurringTaskResponse`, etc.). Add new domain types here rather than colocating them per-component.

**Provider order** (`App.tsx`): `LanguageProvider` wraps `ThemeProvider` wraps `AccessibilityProvider` wraps `BrowserRouter`. All three contexts read/write shared cookies, so keep this nesting if adding related providers.

**`SettingsModal.tsx`'s sections are grouped by what a setting actually *is*, not by when it was added (2026-09-10 reorg)** — Appearance (language, dark mode: purely visual) → Notifications & behavior (reminders, haptic feedback, calendar task visibility: things the app *does*) → Accessibility (colorblind filter, font size) → Support → Danger Zone, in that order. The first two used to be one "Appearance" section; three behavior toggles had accumulated under a visual-settings header they didn't belong under, purely because each was added as "just one more row in the existing section" at the time. When adding a new setting, place it by category rather than defaulting to whichever section is nearest the bottom.

**Accessibility settings (colorblind filter + font size):** `AccessibilityContext.tsx` follows `ThemeContext`'s exact pattern — shared-cookie-then-localStorage priority chain, applied via a class on `documentElement`, both persisted on every change. Both default to "off" (`colorblindMode: "none"`, `fontSize: "medium"`, neither adds a class), so a fresh install/existing user sees no change at all — deliberate, per the "default must be the current look" request this shipped under.
- **Colorblind filter** (`cb-protanopia`/`cb-deuteranopia`/`cb-tritanopia` classes, `src/index.css`) applies a whole-page CSS `filter` to `body` — a portal's content (every `ModalOverlay`-based modal, see `ModalOverlay.tsx`) is a DOM *child* of `document.body`, so it's covered too, same as any other descendant. **Built only from standard `filter` functions** (`hue-rotate()`/`saturate()`/`contrast()`), deliberately *not* a custom SVG `feColorMatrix` referenced via `filter: url(#id)` — that was the original implementation (with well-established Machado/Viénot/Brettel-family matrices, plus a hidden host SVG in `index.html`) and it shipped twice with **zero visible effect in production**, first targeting `html` (theorized as an `html`-specific `filter:url()` reliability issue and moved to `body`) and then targeting `body` too (still nothing) — the actual root cause was never conclusively identified (likely an SVG-filter-reference resolution quirk), so rather than keep guessing at increasingly narrow fixes, the whole `url()`-referenced-filter approach was abandoned. Plain filter functions have no reference resolution or color-interpolation-space ambiguity to get wrong, so "does the toggle visibly do anything" is no longer a live question — only how well-tuned the specific hue-rotate/saturate/contrast values are, which is a far safer thing to be imperfect about. This is a whole-page best-effort assist, not a clinically precise per-user daltonization; don't oversell it as such in UI copy. If a future report says this *still* does nothing, suspect the deploy/cache angle before the CSS itself — see the git log around this note for how that was ruled out each time.
- **Font size** is 5 steps, not 3 (`text-scale-small`/`text-scale-small-medium`/`text-scale-medium-large`/`text-scale-large` classes, no class for `medium` — added 2026-09-10 so there's a step between small/medium and between medium/large, per user request) — scales the root `font-size` — and therefore every `rem`-based Tailwind size utility app-wide — by ×0.875/0.9375/1/1.0625/1.125 of whatever `index.css`'s existing desktop compact-scale rule (`@media (min-width:640px) { html { font-size: 80% } }`, added earlier for an ~80%-zoom look on desktop) currently resolves to per breakpoint, rather than hardcoding absolute values that would fight it — the two new steps sit exactly halfway between their neighbors. If that base 80% ever changes, recompute all 5 percentages in `index.css` to match rather than leaving them stale. This one stays on `html` (unlike the colorblind filter above) — root `font-size` is the standard, well-proven technique for `rem`-based scaling, no equivalent reliability issue. **The picker is `FontSizeSlider.tsx`, not a button row** — a native `<input type="range" min={0} max={4}>` with its default track/thumb fully stripped (`.rc-slider` in `index.css`) and a hand-drawn track/fill/5-tick-marks layer sitting behind it purely for decoration; the native input handles drag/touch/keyboard interaction and screen-reader semantics for free, the CSS layer just makes it look like a single draggable circle instead of a native range input. Chosen over a fully hand-rolled pointer-event slider (the pattern this app otherwise favors for custom drag interactions — long-press-to-select, swipe nav) specifically because a *5-position snapping* slider gets free keyboard support and touch handling from the native element that a from-scratch version would have to reimplement, and getting that reimplementation exactly right isn't worth it here. If a future style change needs the thumb to look meaningfully different across browsers, remember `::-webkit-slider-thumb`/`::-moz-range-thumb` need separate rules (an unsupported pseudo-element inside a shared selector list invalidates the whole rule in some browsers) — don't try to consolidate them into one selector.
- Both are also applied synchronously before React mounts, but as **two separate anti-flicker `<script>` blocks** in `index.html`, not one: dark mode + font size (both target `documentElement`, which exists immediately) stay in the `<head>` script, while the colorblind filter (targets `body`) has to live in its own `<script>` placed right after `<body ...>` opens — `document.body` is still `null` while the parser is inside `<head>`, so a single shared script would silently fail (inside its own `try/catch`) on that line. Neither is imported from the context (this runs before any JS module loads), so a change to the class-application logic needs the same change made by hand in whichever of the two scripts is relevant, plus the context itself.
- `SettingsModal.tsx` exposes both under a new "Accessibility" section (between Appearance and Support) as two chip-button groups (reusing the chip-button visual language `FeedbackModal.tsx`'s category picker established) rather than toggles/dropdowns, calling `useAccessibility()` directly the same way it already calls `useTheme()`/`useLanguage()` — no props threaded through `DashboardPage.tsx` for this.

**Styling:** Tailwind CSS v4 (via `@tailwindcss/vite` plugin, not a PostCSS config file). Dark mode is class-based (`dark` class toggled on `documentElement` by `ThemeContext`), palette centers on `zinc`/`gray` for WCAG contrast. `tsparticles` (the `@tsparticles/slim` bundle, not the full engine) is used for the auth-page interactive background, lazy-loaded with its own `Suspense` boundary so it never blocks the dashboard's initial load. There is no animation library — `framer-motion` was removed (see Bundle size below); simple mount transitions are plain CSS (`transition-*` classes + a two-phase `shouldRender`/`isVisible` state, as in `PageTransition.tsx` and `ModalOverlay.tsx`) rather than reaching for a library.

**i18n:** handled by `LanguageContext` (not an external i18n library) — same cookie+localStorage persistence pattern as theme.

**User feedback:** use `react-hot-toast` (`toast.success/error/loading`) for all user-facing success/error/status messages — not `alert()`. A single `<Toaster />` is mounted once in `App.tsx`'s `AppShell` (theme-aware styling via `useTheme()`), so components just call `toast(...)` directly, no need to render their own `<Toaster />`. For an async flow with a start/end state (e.g. "analyzing..." → "ready"), reuse one toast via its id (`toast.loading(...)` returns an id, pass `{ id }` to the follow-up `toast.success/error`) instead of stacking separate toasts.

**Error boundary:** `src/components/ErrorBoundary.tsx` wraps the whole app (outermost, in `App.tsx`, above `LanguageProvider`/`ThemeProvider`) so a render error anywhere doesn't blank the page. It intentionally doesn't use `ThemeContext`/`LanguageContext` for its fallback UI, since those could be what's broken — it reads `navigator.language` directly instead.

**PWA:** `public/manifest.json` + the meta tags in `index.html` make RedCheck installable ("Add to Home Screen"); when launched from the home screen icon it opens in standalone mode with no browser URL bar. This is the only way to hide the address bar — a normal browser tab can't do that via script. `public/icons/` (`icon-192.png`, `icon-512.png`, `apple-touch-icon.png`) were generated from `public/redcheck.svg` via Inkscape; regenerate them the same way if the logo changes. No service worker/offline support is set up — this is install-for-chrome-hiding only.

**Dashboard data loading:** `DashboardPage.tsx`'s `refreshData()` fetches everything the dashboard needs with a single call, `getSubjectsWithTasks()` (`src/api/subjectApi.ts`, hits `GET /subjects/with-tasks`) — subjects come back with their pending/completed-today tasks already nested (`SubjectWithTasks[]`, `src/types/index.ts`). This replaced a previous N+1: `getSubjects()` followed by one `getTodayTasks(subject.id)` call per subject via `Promise.all`. `getSubjects()`/`getTodayTasks()` still exist and are used elsewhere (e.g. `TrashView.tsx`) for their original narrower purposes — don't reintroduce the per-subject loop in `refreshData()` itself.

**Dashboard search & keyboard shortcuts:** `DashboardPage.tsx` filters subjects/tasks client-side (`filteredSubjects`, a `useMemo` over `subjects` + `searchQuery`) — a subject whose name matches keeps all its tasks, otherwise only its matching tasks are kept. Both the main task list and `OverdueSection` render from `filteredSubjects`, not raw `subjects`, so filtering stays in one place. A single `window` `keydown` listener there also handles Ctrl/Cmd+K (focus the search input) and Escape (closes the mobile drawer / trash view / whichever inline form is open, one layer at a time, or clears the search) — it deliberately skips its own cascade while `SettingsModal`/`SmartCheckModal` are open, since those close on Escape independently.

**Modal Escape-to-close and focus management:** `ModalOverlay.tsx` takes an optional `onClose` and listens for Escape itself while open, so `SettingsModal`, `SmartCheckModal`, and `RecurringTasksModal` all get this for free by passing `onClose={onClose}` through to their `<ModalOverlay>` — add it the same way for any new modal built on this wrapper rather than wiring a listener per-modal. The same wrapper also moves focus into the dialog on open (first focusable element inside it), traps Tab/Shift+Tab within it while open, and restores focus to whatever triggered it on close — all keyed off `isOpen` alone, no extra props needed from callers.

**Bulk task actions:** `DashboardPage.tsx` has a selection mode (`selectionMode` + `selectedTaskKeys`, a `Set<string>` of `"subjectId:taskId"` keys — spans subjects, not scoped per-subject) with two entry points: a "Select" button next to the search bar (`hidden sm:flex` — **desktop only**), and, on mobile, long-pressing any task in `TaskItem` (`onLongPressSelect` prop, gallery-style — touch handlers directly on the row, 500ms hold with a 10px move-cancels-it threshold, same hand-rolled-no-library approach as AgendaView's swipe nav and Sidebar's drawer swipe). Both paths land on the same state: `DashboardPage.tsx`'s `handleLongPressSelectTask` enters selection mode with just the long-pressed task pre-selected, same shape as clicking the desktop button then picking a task by hand. The mobile/desktop split exists because the button used to sit right next to the "sort by priority" toggle and read as cramped on narrow screens — long-press replaces it there rather than trying to fit both buttons. While selection mode is active, tapping **anywhere on a `TaskItem` row** toggles that task's selection (the row's own `onClick` fires `onToggleSelect` when `selectionMode` is true) — not just the checkbox, which is the point of the gallery-style pattern (a small checkbox alone would be a poor touch target for selecting several tasks in a row). The checkbox's own `onClick` only runs `handleToggleTask` when *not* in selection mode; in selection mode it does nothing itself and lets the click bubble up to the row, so a checkbox tap isn't handled twice. Its icon/appearance still switches to a selection checkbox via the `selectionMode` prop, and its edit/delete icon buttons hide. Bulk complete/delete just fan out the existing single-task `toggleTask`/`deleteTask` calls via `Promise.all`, then call `refreshData()` once to resync — no new API endpoints needed. Escape exits selection mode as part of the same cascade as the rest of the dashboard's Escape handling. `OverdueSection` tasks are deliberately not part of any of this (no `selectionMode`/`onLongPressSelect` props there) — bulk selection has never covered overdue tasks.

**Undo-delete toast:** every delete in this app (`deleteTask`/`deleteSubject`) is already a soft-delete on the backend — the item goes to Trash (`TrashView.tsx`) rather than being removed outright, with `restoreTask`/`restoreSubject` as the existing recovery path. `DashboardPage.tsx`'s `showUndoToast(message, onUndo)` (built on `toast.custom`, not the `Toaster`'s built-in styling, since it needs its own action button) rides on top of that: after a single task/subject delete, a calendar delete, or a bulk delete, it shows a 5s dismissible toast with an "Undo" button that calls the matching `restoreTask`/`restoreSubject` + `refreshData()`. This is purely a frontend UX layer — no new backend endpoints — and it's why single task/subject deletes still have **no confirm dialog**: the two-step "delete, then optionally undo" pattern is the recovery mechanism there, on purpose, rather than a confirm-before-delete friction step (irreversible actions — hard-delete-forever in Trash, bulk delete, empty trash, delete account — still go through `useConfirm()`, see below). `handleDeleteTask`/`handleDeleteSubject` track the in-flight optimistic-removal `setTimeout` per id in a ref map (`taskDeleteTimeoutsRef`/`subjectDeleteTimeoutsRef`) so a fast Undo click can cancel it — without that, a click landing inside the 400ms fade-out window would race the timeout, which would then filter the just-restored item right back out of local state.

**Loading states:** prefer a skeleton shaped like the real content over a generic centered spinner — see `src/components/DashboardSkeleton.tsx` (mirrors the sidebar/agenda/tasks/performance layout, including the mobile top/bottom bars, and matches the *default* state — Focus Mode off, so Agenda is shown at its real ~55% width and Performance isn't shown at all — rather than an equal-width guess) and the inline `animate-pulse` placeholder rows in `RecurringTasksModal.tsx`/`TrashView.tsx`. `animate-pulse` on an outer wrapper is enough to pulse every descendant together (CSS opacity composites a whole subtree), so it doesn't need repeating on each block. If the dashboard's default view (Focus Mode, Agenda width, etc.) changes, update the skeleton to match or it'll visibly jump on load.

**Recurring task editing is centralized in two shared components (2026-09-09), not duplicated per screen.** Three surfaces create/edit routines — `SubjectSection.tsx`'s create form, `RecurringTasksModal.tsx`'s per-subject inline edit form, and `RoutinesView.tsx`'s global inline edit form — and all three build around the same two pieces so they can't drift out of sync with each other:
- **`RecurrenceFieldset.tsx`** owns every recurrence-picking control: the frequency `<select>` (`NONE`/4 presets/`CUSTOM`), the weekly-vs-monthly pill toggle shown only for `CUSTOM`, the day picker for whichever sub-mode is active (`WeekdayPicker.tsx`'s 7-chip row, or a plain day-of-month `<select>` with a "last day" option), the time/end-date inputs, and the live `RecurrencePreview.tsx`. It's fully controlled — one `value: RecurrenceState` + one `onChange` — and takes `compact` (SubjectSection's full-size inputs+labels vs. the two modals' denser, label-less inputs) and `allowNone` (false in both edit contexts — an existing routine is always recurring, so "Does not repeat" isn't offered there) to cover the two visual densities and two use cases without forking the component.
- **`RoutineRow.tsx`** owns the view-mode row (title, frequency/time/end-date/streak/next-occurrence badges, edit/pause/delete buttons) shown by both `RecurringTasksModal.tsx` and `RoutinesView.tsx`; the latter also passes a `subjectChip` (subject color dot + name) and `showCompletionRate`, both absent in the per-subject modal to keep that list lighter — the global view is deliberately the "full stats" surface, the per-subject one the "quick glance."

**`recurrenceUtils.ts` is the single place that knows the on-the-wire shapes** — keep it in sync with the backend's `FrequencyUtils` if either ever changes:
- Custom weekly: a restricted 6-field cron string, `"0 0 0 * * <days>"` (`buildCustomFrequency`/`parseCustomFrequencyDays`), `<days>` a comma-separated list of 0-6 using JS's own `Date#getDay()` numbering (Sunday=0). `MONDAY_FIRST_CRON_DAYS` maps that Sunday-first storage order to the Monday-first display order used everywhere else in the app (`AgendaView.tsx`'s `weekDays`).
- Custom monthly: **not** cron — `"MONTHLY:<day>"`, `<day>` 1-31 or the literal `"LAST"` (`buildMonthlyDayFrequency`/`parseMonthlyDayFrequency`), same reasoning as the backend (`FrequencyUtils`'s own comment): no Quartz-style "L" in Spring's `CronExpression`, and a raw day-of-month cron field would silently skip short months instead of clamping.
- `formatFrequencyLabel` is the single function that turns any stored frequency — preset, custom weekly, or custom monthly — into its display label; `RoutineRow` uses it so both surfaces read a frequency identically.
- `parseFrequencyForEditing`/`resolveFrequency` are the inverse pair a `RecurrenceState` round-trips through: `parseFrequencyForEditing(task.frequency)` populates an edit form, `resolveFrequency(...)` turns the form's state back into the wire string on submit. `isRecurrenceStateValid` is the one client-side guard (blocks "Custom + Weekly" with zero days checked) — mirrors the backend's own validation so a doomed request is never sent.
- `getUpcomingOccurrences` powers `RecurrencePreview.tsx`'s "next few dates" line, computed entirely client-side (no network round trip, so it updates instantly as the user picks options) — a deliberate mirror of the backend's `RecurringTaskService#computeNextOccurrence`, not an independent guess: the first occurrence is always "tomorrow" regardless of frequency (matching `RecurringTaskSchedulerService#shouldGenerate`'s short-circuit for a routine that's never generated before — even a custom Mon/Thu pattern's first-ever task can land on a Friday), and only occurrence #2 onward actually steps forward via the frequency pattern. `RoutineRow`'s badges show the persisted, **server-computed** truth instead (`task.time`/`task.endDate`/`task.nextOccurrence`/`task.currentStreak`/etc. straight from the API response) — a paused routine shows "Paused" in that slot rather than a stale next-date.

**The global routines overview (`RoutinesView.tsx`, 2026-09-09)** is a full-screen view swapped into the same main-content slot as `TrashView.tsx` (`DashboardPage.tsx`'s `showRoutines` boolean, mirroring `showTrash` exactly — mutually exclusive with it, both togglable from `Sidebar.tsx`'s footer and the command palette) rather than a modal, since it's a genuine "browse everything" screen like Trash, not a quick action. It fetches every routine across every subject in one call (`GET /recurring-tasks`, `getAllRecurringTasks()` — see the backend's `RecurringTaskOverviewController`) and joins each one to its subject's name/color **locally**, from the `subjects` prop `DashboardPage.tsx` already holds in state — the response DTO deliberately doesn't carry a denormalized subject name. Routines are grouped by subject (subjects with zero routines just don't get a section) and prefixed with a 3-stat summary strip (active count, best streak across everything, average completion rate over routines that have generated at least one task) — deliberately simple numbers, no charts, to match this view's "digest" role rather than turning it into a dashboard of its own. Its header/summary-strip sizing is responsive (`sm:`-gated padding/text/icon sizes) — it's the one screen in this pair with a subtitle line and a 3-column stat strip, neither of which `TrashView.tsx`'s pattern (which this view otherwise mirrors) has to account for, so don't assume copying that pattern verbatim is automatically mobile-safe.

**A `truncate` span that's a flex *item* (not a plain block child) needs `min-w-0` on that same element, or the ellipsis never triggers and the row silently forces the page wider instead.** `RoutineRow.tsx`'s frequency/description line (`<p className="flex items-center gap-1.5">` containing badge spans + a `truncate` description span) hit this for real: a flex item's default `min-width` is its own content's intrinsic size, which *overrides* `truncate` — the item just refuses to shrink below that, and since nothing between it and `DashboardPage.tsx`'s own `overflow-x-auto` wrapper clips overflow (every intermediate block is `overflow: visible` by default), a single long task description silently widened the *entire page*, forcing a large amount of horizontal scroll to see content that had scrolled off — not a layout glitch confined to that one row (fixed 2026-09-09; same fix applied to the `subjectChip` name span, capped at `max-w-[7rem]` too since a subject name has no length limit either). This is easy to reintroduce: any time you add `truncate` to something that is *itself* a flex child (as opposed to a plain block element inside a width-constrained flex item, like `RoutineRow`'s own title line, which needs no `min-w-0` because the `<p>` isn't a flex item of anything), pair it with `min-w-0` on that same element and verify with an unrealistically long test string, not just typical demo data.

**That fix alone turned out not to be a hard guarantee (2026-09-09 follow-up)** — fixing the one known-overflowing element doesn't rule out some *other* element (a stat label's single long uppercase word with no break point, some future addition, etc.) doing the same thing later, and `DashboardPage.tsx`'s shared `overflow-x-auto` wrapper (the one around the Trash/Routines/dashboard-3-block swap, kept as a safety net for the dashboard's own 3-block tablet-width squeeze — see the comment above it) means *any* single overflowing descendant anywhere in whichever view is currently mounted turns into page-wide horizontal scroll, not a glitch contained to that element. Two belt-and-suspenders layers now sit between that shared scroller and `RoutinesView`'s content so this class of bug can't resurface even from an element nobody thought to check: the `flex-1 sm:ml-4` wrapper around both `<TrashView>` and `<RoutinesView>` in `DashboardPage.tsx` now also carries `min-w-0` (lets that flex item actually shrink to its allotted share instead of being forced wide by a child's content), and `RoutinesView.tsx`'s own root carries `min-w-0 overflow-x-hidden` alongside its existing `overflow-y-auto` (clips any remaining internal horizontal overflow locally — worst case something clips at the card's own edge, which is still strictly better than the whole page gaining a horizontal scrollbar). If a future addition to this view genuinely needs to be wider than the card, it needs an intentional `overflow-x-auto` on that one element specifically, not a removal of the guard on the root.

**Task reminders:** `DashboardPage.tsx` polls pending tasks every 60s (plus once immediately) for ones due within the next 30 minutes, firing a `toast(...)` and a browser `Notification` for each (deduped per task via `remindedTaskIdsRef`, a `Set` of task IDs). This is client-side only — no service worker, no backend push — so it only fires while RedCheck is open in a tab or installed PWA, never when closed. Enabled via a Settings-modal toggle (`remindersEnabled`, persisted in `localStorage`) that calls `Notification.requestPermission()` on first enable. The firing code deliberately does **not** re-check the static `Notification.permission` getter before calling `new Notification(...)` — that getter was observed to lag behind the resolved `requestPermission()` result (at least under headless/CDP-driven browsers) — it trusts `remindersEnabled` instead (which only becomes true right after a "granted" resolution) and wraps the call in try/catch as the real safety net. A real push-notification system (works when the app is closed) needs a service worker, VAPID keys, a subscription endpoint, and a backend trigger — none of that exists yet; this reminder system is deliberately the lighter-weight alternative.

**Task-completion feedback:** `src/utils/feedback.ts` exports `triggerHapticFeedback(duration = 40)` (Vibration API), feature-detected/try-caught so it no-ops (returns `false`) where unsupported (e.g. no Vibration API on iOS Safari — a permanent WebKit limitation, not fixable from here) rather than throwing. **AgendaView (calendar):** `getTasksForDate(subjects, date)` (module-scope, not a closure) filters `subjects` down to tasks due on a given day — this is the live, always-in-sync source, but (like the rest of the dashboard) only ever has *pending or completed-today* tasks, since it's fed by `subjects` (`getSubjectsWithTasks()`, dashboard-scoped). For a **past** date that's not enough (a task completed three days ago has no representation in `subjects` at all), so every call site actually goes through `getMergedTasksForDate(date)` instead of `getTasksForDate` directly: today/future dates still resolve via `getTasksForDate(subjects, date)` unchanged, but a strictly-past date resolves via `getHistoricalTasksForDate(historicalTasks, subjectNameById, date)` — a parallel filter over `historicalTasks`, a flat `TaskResponse[]` fetched from the backend's `GET /tasks?from=&to=` (`getTasksForDateRange` in `taskApi.ts`), which unlike `subjects` includes completed tasks. `isDateInPast(date, today)` (`date < today && date.toDateString() !== today.toDateString()`) is the single past/not-past test shared by all of this.

`historicalRange` (a `useMemo`) computes the from/to bounds actually visible — a single day (Day view), the visible Monday–Sunday (Week view), or the 1st–last day of the displayed month (Month view; adjacent-month cells in the grid are blank, see `calendarCells`, so the range never needs to spill into neighboring months). A `useEffect` keyed on `historicalRange` fetches exactly once per navigation, and **only** when `historicalRange.from` is itself in the past — browsing entirely future dates does zero extra network calls. This range-based, one-call-per-view-change design deliberately avoids per-day fetching (a 42-cell Month view firing 42 requests) the same way `GET /subjects/with-tasks` avoids the dashboard's old per-subject N+1.

Because past-day chips now render real, editable tasks (not just a heatmap count), a create/update/delete/toggle reaching the calendar for a past date needs `historicalTasks` to reflect it immediately, not just after the next navigation re-triggers the effect — `refreshHistory()` bumps a `historyRefreshTick` counter (in the effect's deps) after each of the four mutation paths: `rescheduleTask` (drag-and-drop), `renderCompleteToggle`'s click handler, and `CalendarTaskModal`'s `onCreate`/`onUpdate`/`onDelete` (wrapped as `handle*TaskFromCalendar` specifically to add this, since the modal is otherwise handed the raw `DashboardPage` callbacks directly). If a 5th mutation path is ever added here, wire it the same way rather than assuming `subjects`-driven re-render is enough.

The heatmap (`getProgressHeatmap()`) fallback badge (`completed/total` count) still exists but now only fires when `getMergedTasksForDate` returns zero rows for a past day with a nonzero heatmap count — e.g. a day whose only task was later hard-deleted. It's no longer the primary way past days are shown.

Progress heatmap coloring (Month/Week backgrounds): `getSquareColor(dateString)` colors a past/today cell by that day's `records[dateString]` completion ratio (white→red→light green→green, see the function itself) — it's a single choke point deliberately checked first thing for a `heatmapEnabled` prop (defaults **on**), toggled from **Settings** (`SettingsModal.tsx`'s "Notifications & behavior" section, right below "Tasks in calendar") rather than a control living inside the calendar itself. This was originally local state inside `AgendaView.tsx` with a `Palette` icon button in its own header — moved up to `DashboardPage.tsx` (2026-09-10, per user request, same move `showTasksInCalendar` got earlier) to sit next to the app's other preferences instead of being the one calendar-specific setting still hidden inside the calendar; still the exact same `localStorage` key (`rc_calendar_heatmap_enabled`) so an existing user's choice carries over untouched. Disabling it makes `getSquareColor` always return the neutral background, *without* touching the `isToday` red highlight or the "current week" tint that layer on top downstream — those read as navigational cues, not the completion-ratio heatmap itself, so they stay regardless of the toggle — and it's independent of `showTasksInCalendar` (a day can show colored-but-empty cells, task-chips-but-uncolored, both, or neither). A day with real task chips to show never needed the heatmap color to convey anything; Month view used to also show a `record.completedTasks/record.totalTasks` "Tasks x/y" fallback card for a past day with zero real task chips (e.g. its tasks were later hard-deleted) — removed per user request, so that case now just renders an empty cell body instead.

**Show/hide tasks in the calendar (Settings toggle, 2026-09-10):** `AgendaView`'s `showTasks` prop (default `true`, wired from `DashboardPage.tsx`'s `showTasksInCalendar` state, `localStorage` under `rc_show_tasks_in_calendar`, same opt-out `!== "false"` pattern as `taskFeedbackEnabled`) is checked first thing inside `getMergedTasksForDate` — the single function Day/Week/Month all read task data through — and short-circuits to `[]` when off. This is a **separate, independent** toggle from `heatmapEnabled` above: disabling task display doesn't touch the heatmap's completion-ratio coloring (that reads from the separately-fetched `records`, not from `subjects`/`getMergedTasksForDate` at all), and disabling the heatmap doesn't hide tasks — a user can mix-and-match a "clean, dates-only" calendar with or without the color signal. Creating/rescheduling a task from the calendar (the "+" affordances, clicking a day) stays fully functional either way — this only gates *reading* existing task data for display, not the calendar's own navigation or task-mutation paths.

Subject color coding: `getSubjectColor(subjectId)` (`SUBJECT_COLOR_PALETTE`, 8 Tailwind color families, keyed by `subjectId % length`) gives every pending task a stable color regardless of array order/filtering — used by Day view's two task-card renderers, Week view's day-cell cards, and Month view's day-cell chips. Completed tasks always render gray/muted instead, ignoring subject color. Month view shows up to 2 truncated task-title chips per cell (`+N {t.moreTasks}` beyond that, `WEEK_CELL_TASK_LIMIT`-style cap inline). Week's cells are one tall row instead of Month's up to six short ones, so it deliberately doesn't reuse Month's plain chip: each task is a fuller card (subject-tinted bg/text, a priority-colored `border-l-2` *and* a matching dot, plus the time), capped at `WEEK_CELL_TASK_LIMIT` (6, fixed 2026-09-09) before falling back to "+N more" — see Month's own inline chip for the plainer variant.

Jump-to-date: a `CalendarDays` icon button folded into the existing prev/Today/next pill (not a separate boxed control) opens a hidden native `<input type="date">` via `showPicker()` (falling back to `.click()` if unsupported), and its `onChange` calls `setCurrentDate` directly — cheap and accessible compared to hand-rolling a date-picker popover. The header row (`AgendaView.tsx`'s `--- HEADER ---` section) runs at the edge of its available width once the calendar column shrinks (fixed-width sidebar + fixed-width right panel on desktop), so that row needs `flex-wrap` — without it, extra header content (like this button) silently overflows past the panel edge instead of wrapping to a second line.

Day view places tasks on the hourly grid (`timedTasksByHour`, keyed by `d.getHours()`) instead of floating an unrelated list over it, plus an `allDayTasks` strip above the grid for deadlines with no time component. `DAY_VIEW_HOUR_START`/`DAY_VIEW_HOUR_END` are `0`/`23` (full day, fixed 2026-09-09 — it used to be an 8–20 window, which hid any task outside typical working hours) and `hours` is `Array.from({ length: DAY_VIEW_HOUR_END - DAY_VIEW_HOUR_START + 1 }, ...)`, always derive it from the constants rather than hardcoding the row count again. Since the grid now always spans the full day, it opens scrolled past the empty early-morning hours: a `dayScrollRef` + `useEffect` (keyed on `[view, currentDate]`) sets `scrollTop` to the current hour on today, or 8am on any other day, whenever Day view becomes active. Several things matter if this is touched again:
- **The hour-label column and the grid+tasks column must share one `overflow-y-auto` scroll container, never two independent ones.** They did originally (each column scrolled on its own) and it was invisible because the old task list wasn't tied to specific hours; the moment tasks became hour-row-aligned, any drift between two independently-scrolling siblings became visibly broken misalignment.
- **Each hour row needs `shrink-0`.** Without it, flexbox lets 80px (`h-20`) rows compress below that height when the column's total content (24 hours) exceeds the visible area — rows with a task resist shrinking below their content's min-height while empty rows compress freely, drifting the whole grid out of alignment. `renderCompactHourTask` (single-line, for the grid) is deliberately more compact than `renderDayTaskCard` (the fuller card, used only in the all-day strip which isn't height-constrained) — the fuller card doesn't fit two of itself inside one fixed 80px row even with an overflow fallback, which is what motivated having two card variants instead of one.
- **The grid column's ruled-line background needs `bg-origin-content`, not the default `padding-box`.** The `linear-gradient` ruled-line pattern (`bg-[size:100%_5rem]`) tiles from the background's *origin box* — `padding-box` by default means it starts at the box's outer edge, before the `p-3 sm:p-6` padding is applied, while the actual hour-row content starts *after* that padding. That mismatch is what made the ruled lines visibly drift out of sync with the real hour rows below (fixed 2026-09-09) — `bg-origin-content` anchors the pattern to the content box instead, so it starts in the same place the rows do.
- **The red "now" line's `top` is a hand-computed `rem` offset** (`(hour - DAY_VIEW_HOUR_START) * 5 + minutes/12`, assuming exactly 80px/hour) applied via a `--now-offset` CSS custom property, plus a Tailwind arbitrary-value `top-[calc(0.75rem+var(--now-offset))] sm:top-[calc(1.5rem+var(--now-offset))]`. The `0.75rem`/`1.5rem` base is the grid column's own `p-3`/`sm:p-6` top padding — the line is absolutely positioned inside that padded, `relative` column, and CSS measures an absolutely-positioned element's `top` from the *padding box*, not the content box, so without adding that padding back in the line renders above where hour 0 actually starts (fixed 2026-09-09, same root cause class as the ruled-line bug above). If the hour range, row height, or that padding ever changes, update this formula too.
- **The pulsing dot on that line is centered via `-translate-x-1/2 -translate-y-1/2` on `absolute left-0 top-0`, not `flex items-center`.** Centering a flex child only lands it on the border line if the flex container's own box height happens to equal the child's height — it didn't here (the container had no explicit height, and centering a same-size child inside a same-size box is a no-op that leaves the dot's center sitting a full half-dot-height *below* the actual `border-t-2` line instead of on it), so the dot visibly trailed the line (fixed 2026-09-09). `translate(-50%,-50%)` centers on the container's exact (0,0) corner regardless of any box-sizing coincidence.
- **Both columns need `self-start`.** Without it, flexbox's default `align-items: stretch` caps each column's own box at the scroll container's *visible* height (the only definite height its `flex-1` parent gives it) instead of its full 24-row content height. The row `div`s still render past that point — a block child overflowing a `visible`-overflow parent isn't clipped — but each column's own background only paints up to that capped box, so the grey label backdrop and the ruled-line gradient both visibly stopped partway down (around the middle of the day) while the hour numbers kept appearing below them (fixed 2026-09-09). `self-start` sizes each column to its natural content height instead, so scrolling reveals background all the way to hour 23.
- **The ruled-line/grey-column grid must always render all 24 hour rows, even on a day with zero tasks.** It used to swap the whole hour-row grid out for a small "day off" placeholder box when `tasksForCurrentDay.length === 0`, which — combined with `self-start` above — meant the ruled-line column's *own* natural content height collapsed to just that small placeholder's height on an empty day, since self-start sizes a column to its own content, not to its sibling's. The grey label column (always 24 real rows, unconditional) stayed full height regardless, so only days with at least one task got a full-height background; empty and non-empty days visibly alternated as the user paged through the week (fixed 2026-09-09). The fix: the hour-row grid renders unconditionally, and the "day off" message is an additional overlay (not a replacement) layered on top of it.
- **That "day off" overlay must be `position: absolute`, not `sticky`.** `sticky` was tried first (with `top-0 h-0` on its wrapper so it wouldn't add flow height) to keep it visible near whatever hour the view happened to be scrolled to — but a sticky element only overrides its position once its own natural in-flow position would scroll past the threshold, and this element's natural position, placed after the 24-row grid in the DOM, is at the very *bottom* of the (~1920px tall) column. So it just sat there unstuck at the bottom instead of pinning near the top (fixed 2026-09-09). `absolute` (positioned like the "now" line in the same `relative` column) takes it out of flow entirely, so it's guaranteed not to affect the column's own content height/ruled-lines regardless of DOM order — and the Day-view scroll-to-hour effect (`dayScrollRef`) scrolls an empty day straight to the top (`scrollTop = 0`, added as a branch keyed on `tasksForCurrentDay.length === 0`) so this absolutely-positioned-near-the-top card is actually visible without the user having to scroll up first.

Week and Month view headers (`grid grid-cols-7`, day names/dates) sit directly above a separate `grid grid-cols-7` body (day cells) — two independent grid containers. The body has `gap-1.5 p-1.5` (a visual gutter between cells); if the header doesn't have the *same* `gap-1.5` plus matching horizontal padding, its 7 columns compute to a different width than the body's 7 columns (full-width columns vs. columns narrowed by the gutter's gap+padding), so header labels drift further out of alignment with their column below at each successive column. Both headers now carry `gap-1.5 px-1.5` for exactly this reason (fixed 2026-09-09) — keep them in sync with the body's gutter values if that ever changes.

Create/reschedule from the calendar: `CalendarTaskModal.tsx` is a single modal (built on `ModalOverlay`, like the app's other modals) that handles both creating a new task (a "+" affordance on hover in Month/Week cells and Day-view hour rows, plus an "Add task" button in Day view's empty-day state) and editing/rescheduling an existing one (clicking any task chip/card in Day/Week/Month). AgendaView owns a single `taskModalState` (`{mode:"create", date, defaultSubjectId} | {mode:"edit", task} | null`) and passes `onCreateTask`/`onUpdateTask`/`onDeleteTask` callbacks down from `DashboardPage.tsx` (`handleCalendarCreateTask` etc.), which call the same `taskApi.ts` functions as the existing inline per-subject forms and update the same `subjects` state — so a change made from the calendar shows up in the Tasks panel immediately and vice versa. This modal is deliberately self-contained (not just reusing the Tasks panel's inline edit form) because the Tasks panel isn't on screen at the same time as the calendar on mobile (separate bottom-nav tabs) — the calendar's create/reschedule flow has to work standalone. Every task-chip/cell click that opens this modal calls `e.stopPropagation()` first, since the same click target's parent cell already has its own `onClick` (navigate to Day view for that date).

**Day/Week/Month selector's sliding pill (fixed 2026-09-10):** the pill's position/width math (`translateX(index * 100%)`, `width: calc((100% - 0.5rem) / 3)`) hardcodes "each button is exactly 1/3 of the row" — so all three view buttons must stay `flex-1` (equal width) at every breakpoint, never `flex-initial`/content-sized. A `sm:flex-initial` variant here once let "Week"/"Month" (longer labels) render wider than "Day" on `sm:` and up, desyncing the pill from the real button boxes — visibly off-center/asymmetric margins behind whichever label wasn't exactly 1/3 of the row. If this selector's markup changes again, keep the three buttons' widths identical or rework the pill to measure real button positions instead of assuming equal thirds.
