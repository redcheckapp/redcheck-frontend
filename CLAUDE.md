# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

RedCheck is an interactive time/task management SPA that uses AI ("SmartCheck AI") to prioritize daily workloads (risk level, execution order, reasoning). This repo is the **frontend only** — the backend lives in a sibling repo at `../redcheck-backend` (not part of this working directory, but available locally for reference if API contract context is needed).

Write new code comments and commit messages in English, even though some existing code (e.g. `ThemeContext.tsx`) has Spanish comments/names.

Commits follow Conventional Commits style: `feat: ...`, `fix: ...`, `chore: ...`, `refactor: ...`, `docs: ...`, etc.

Automated tests use Vitest + React Testing Library (added 2026-09-09) — see the Testing section below. Coverage is intentionally a smoke-test layer (renders without crashing, key interactions), not exhaustive; don't assume every component has a test.

## Commands

```bash
npm run dev         # start Vite dev server
npm run build       # vite build (bundles only — does NOT type-check; run `npx tsc -b --noEmit` separately, e.g. before committing)
npm run lint        # eslint .
npm run preview     # preview the production build locally
npm run test        # vitest run — one-shot, CI-friendly
npm run test:watch  # vitest — interactive watch mode
```

## Environment

- `VITE_API_URL` — base URL for the backend API, consumed by `src/api/axiosConfig.ts` at build time. Set via `.env` locally, or passed as a Docker build ARG in production (see `Dockerfile`).
- Production deploy is Docker + NGINX: Vite build output is served statically, and NGINX reverse-proxies API paths (`/auth`, `/users`, `/subjects`, `/tasks`, `/recurring_tasks`, `/progress_records`, `/notifications`, `/ai`, etc.) to the backend container. See `nginx.conf` for the exact route table if adding a new API domain that needs proxying.

## Architecture

**Layering:** the codebase strictly separates presentation from data access from global state:

- `src/api/` — one file per backend domain (`authApi.ts`, `taskApi.ts`, `subjectApi.ts`, `recurringTaskApi.ts`, `progressRecordApi.ts`, `smartCheckApi.ts`, `userApi.ts`, `registerApi.ts`), all built on a shared Axios instance in `axiosConfig.ts`. That instance auto-attaches `Authorization: Bearer <token>` from `localStorage` via a request interceptor — new API calls should go through this `api` instance rather than raw `axios`/`fetch`, and API functions should be fully typed against `src/types/index.ts`. A response interceptor there also clears the token and redirects to `/login` on a 401 for a request that carried a token (a plain failed-login 401, with no token yet, is left alone so the caller's own error message still shows).
- `src/context/` — global state via React Context, not a state library. `ThemeContext` and `LanguageContext` follow the same pattern: state is initialized with a priority chain (shared cookie → `localStorage` → system/browser preference) and persisted back to both a shared cookie and `localStorage` on change. If adding another cross-page persisted preference, follow this same cookie+localStorage dual-write pattern via `src/utils/cookies.ts` (`getSharedCookie`/`setSharedCookie`) rather than introducing a new mechanism.
- `src/pages/` — route-level components, wired up in `src/App.tsx` (`react-router-dom` `BrowserRouter`/`Routes`). Current routes: `/`, `/login`, `/register`, `/dashboard`, `/terms`, `/privacy`.
- `src/components/` — reusable, mostly presentational UI. Heavy use of `createPortal` for floating elements (modals, tooltips) to avoid `z-index` stacking issues — follow this pattern for new overlay/modal components rather than relying on z-index alone.
- `src/components/Sidebar.tsx` — the "Analyze Risks" button and the "SmartCheck AI / Analysis Engine" label are intentionally hidden (not deleted) behind `SHOW_RISK_ANALYSIS_BUTTON` / `SHOW_ANALYSIS_ENGINE_LABEL` flags at the top of the file, per a product decision to not expose them yet — flip the flag to `true` to bring one back rather than re-implementing it. The collapsed-sidebar sparkle icon (desktop only, `sm:` and up) is the intended replacement AI hint: visible while the sidebar is collapsed, fades out on expand, never rendered on mobile. The mobile drawer also supports swipe-to-close (drag left past ~30% of its width), implemented with raw `onTouchStart/Move/End` handlers rather than a gesture library — keep that pattern if extending the gesture.
- `src/types/index.ts` — single shared file for API request/response and domain types (`TaskResponse`, `SubjectResponse`, `RecurringTaskResponse`, etc.). Add new domain types here rather than colocating them per-component.

**Provider order** (`App.tsx`): `LanguageProvider` wraps `ThemeProvider` wraps `BrowserRouter`. Both contexts read/write shared cookies, so keep this nesting if adding related providers.

**Styling:** Tailwind CSS v4 (via `@tailwindcss/vite` plugin, not a PostCSS config file). Dark mode is class-based (`dark` class toggled on `documentElement` by `ThemeContext`), palette centers on `zinc`/`gray` for WCAG contrast. `tsparticles` (the `@tsparticles/slim` bundle, not the full engine) is used for the auth-page interactive background, lazy-loaded with its own `Suspense` boundary so it never blocks the dashboard's initial load. There is no animation library — `framer-motion` was removed (see Bundle size below); simple mount transitions are plain CSS (`transition-*` classes + a two-phase `shouldRender`/`isVisible` state, as in `PageTransition.tsx` and `ModalOverlay.tsx`) rather than reaching for a library.

**i18n:** handled by `LanguageContext` (not an external i18n library) — same cookie+localStorage persistence pattern as theme.

**User feedback:** use `react-hot-toast` (`toast.success/error/loading`) for all user-facing success/error/status messages — not `alert()`. A single `<Toaster />` is mounted once in `App.tsx`'s `AppShell` (theme-aware styling via `useTheme()`), so components just call `toast(...)` directly, no need to render their own `<Toaster />`. For an async flow with a start/end state (e.g. "analyzing..." → "ready"), reuse one toast via its id (`toast.loading(...)` returns an id, pass `{ id }` to the follow-up `toast.success/error`) instead of stacking separate toasts.

**Error boundary:** `src/components/ErrorBoundary.tsx` wraps the whole app (outermost, in `App.tsx`, above `LanguageProvider`/`ThemeProvider`) so a render error anywhere doesn't blank the page. It intentionally doesn't use `ThemeContext`/`LanguageContext` for its fallback UI, since those could be what's broken — it reads `navigator.language` directly instead.

**PWA:** `public/manifest.json` + the meta tags in `index.html` make RedCheck installable ("Add to Home Screen"); when launched from the home screen icon it opens in standalone mode with no browser URL bar. This is the only way to hide the address bar — a normal browser tab can't do that via script. `public/icons/` (`icon-192.png`, `icon-512.png`, `apple-touch-icon.png`) were generated from `public/redcheck.svg` via Inkscape; regenerate them the same way if the logo changes. No service worker/offline support is set up — this is install-for-chrome-hiding only.

**Dashboard data loading:** `DashboardPage.tsx`'s `refreshData()` fetches everything the dashboard needs with a single call, `getSubjectsWithTasks()` (`src/api/subjectApi.ts`, hits `GET /subjects/with-tasks`) — subjects come back with their pending/completed-today tasks already nested (`SubjectWithTasks[]`, `src/types/index.ts`). This replaced a previous N+1: `getSubjects()` followed by one `getTodayTasks(subject.id)` call per subject via `Promise.all`. `getSubjects()`/`getTodayTasks()` still exist and are used elsewhere (e.g. `TrashView.tsx`) for their original narrower purposes — don't reintroduce the per-subject loop in `refreshData()` itself.

**Dashboard search & keyboard shortcuts:** `DashboardPage.tsx` filters subjects/tasks client-side (`filteredSubjects`, a `useMemo` over `subjects` + `searchQuery`) — a subject whose name matches keeps all its tasks, otherwise only its matching tasks are kept. Both the main task list and `OverdueSection` render from `filteredSubjects`, not raw `subjects`, so filtering stays in one place. A single `window` `keydown` listener there also handles Ctrl/Cmd+K (focus the search input) and Escape (closes the mobile drawer / trash view / whichever inline form is open, one layer at a time, or clears the search) — it deliberately skips its own cascade while `SettingsModal`/`SmartCheckModal` are open, since those close on Escape independently.

**Modal Escape-to-close and focus management:** `ModalOverlay.tsx` takes an optional `onClose` and listens for Escape itself while open, so `SettingsModal`, `SmartCheckModal`, and `RecurringTasksModal` all get this for free by passing `onClose={onClose}` through to their `<ModalOverlay>` — add it the same way for any new modal built on this wrapper rather than wiring a listener per-modal. The same wrapper also moves focus into the dialog on open (first focusable element inside it), traps Tab/Shift+Tab within it while open, and restores focus to whatever triggered it on close — all keyed off `isOpen` alone, no extra props needed from callers.

**Bulk task actions:** `DashboardPage.tsx` has a selection mode (`selectionMode` + `selectedTaskKeys`, a `Set<string>` of `"subjectId:taskId"` keys — spans subjects, not scoped per-subject) with two entry points: a "Select" button next to the search bar (`hidden sm:flex` — **desktop only**), and, on mobile, long-pressing any task in `TaskItem` (`onLongPressSelect` prop, gallery-style — touch handlers directly on the row, 500ms hold with a 10px move-cancels-it threshold, same hand-rolled-no-library approach as AgendaView's swipe nav and Sidebar's drawer swipe). Both paths land on the same state: `DashboardPage.tsx`'s `handleLongPressSelectTask` enters selection mode with just the long-pressed task pre-selected, same shape as clicking the desktop button then picking a task by hand. The mobile/desktop split exists because the button used to sit right next to the "sort by priority" toggle and read as cramped on narrow screens — long-press replaces it there rather than trying to fit both buttons. While selection mode is active, `TaskItem`'s own complete-toggle checkbox doubles as the selection checkbox (`selectionMode` prop switches its behavior/appearance), and its edit/delete icon buttons hide. Bulk complete/delete just fan out the existing single-task `toggleTask`/`deleteTask` calls via `Promise.all`, then call `refreshData()` once to resync — no new API endpoints needed. Escape exits selection mode as part of the same cascade as the rest of the dashboard's Escape handling. `OverdueSection` tasks are deliberately not part of any of this (no `selectionMode`/`onLongPressSelect` props there) — bulk selection has never covered overdue tasks.

**Undo-delete toast:** every delete in this app (`deleteTask`/`deleteSubject`) is already a soft-delete on the backend — the item goes to Trash (`TrashView.tsx`) rather than being removed outright, with `restoreTask`/`restoreSubject` as the existing recovery path. `DashboardPage.tsx`'s `showUndoToast(message, onUndo)` (built on `toast.custom`, not the `Toaster`'s built-in styling, since it needs its own action button) rides on top of that: after a single task/subject delete, a calendar delete, or a bulk delete, it shows a 5s dismissible toast with an "Undo" button that calls the matching `restoreTask`/`restoreSubject` + `refreshData()`. This is purely a frontend UX layer — no new backend endpoints — and it's why single task/subject deletes still have **no confirm dialog**: the two-step "delete, then optionally undo" pattern is the recovery mechanism there, on purpose, rather than a confirm-before-delete friction step (irreversible actions — hard-delete-forever in Trash, bulk delete, empty trash, delete account — still go through `useConfirm()`, see below). `handleDeleteTask`/`handleDeleteSubject` track the in-flight optimistic-removal `setTimeout` per id in a ref map (`taskDeleteTimeoutsRef`/`subjectDeleteTimeoutsRef`) so a fast Undo click can cancel it — without that, a click landing inside the 400ms fade-out window would race the timeout, which would then filter the just-restored item right back out of local state.

**Loading states:** prefer a skeleton shaped like the real content over a generic centered spinner — see `src/components/DashboardSkeleton.tsx` (mirrors the sidebar/agenda/tasks/performance layout, including the mobile top/bottom bars, and matches the *default* state — Focus Mode off, so Agenda is shown at its real ~55% width and Performance isn't shown at all — rather than an equal-width guess) and the inline `animate-pulse` placeholder rows in `RecurringTasksModal.tsx`/`TrashView.tsx`. `animate-pulse` on an outer wrapper is enough to pulse every descendant together (CSS opacity composites a whole subtree), so it doesn't need repeating on each block. If the dashboard's default view (Focus Mode, Agenda width, etc.) changes, update the skeleton to match or it'll visibly jump on load.

**Task reminders:** `DashboardPage.tsx` polls pending tasks every 60s (plus once immediately) for ones due within the next 30 minutes, firing a `toast(...)` and a browser `Notification` for each (deduped per task via `remindedTaskIdsRef`, a `Set` of task IDs). This is client-side only — no service worker, no backend push — so it only fires while RedCheck is open in a tab or installed PWA, never when closed. Enabled via a Settings-modal toggle (`remindersEnabled`, persisted in `localStorage`) that calls `Notification.requestPermission()` on first enable. The firing code deliberately does **not** re-check the static `Notification.permission` getter before calling `new Notification(...)` — that getter was observed to lag behind the resolved `requestPermission()` result (at least under headless/CDP-driven browsers) — it trusts `remindersEnabled` instead (which only becomes true right after a "granted" resolution) and wraps the call in try/catch as the real safety net. A real push-notification system (works when the app is closed) needs a service worker, VAPID keys, a subscription endpoint, and a backend trigger — none of that exists yet; this reminder system is deliberately the lighter-weight alternative.

**Forgot password:** not implemented — `redcheck-backend` has no password-reset endpoints yet (no email sending, no reset-token issuance/validation). Deferred until backend adds them; don't build frontend-only UI against undefined endpoints.

**Task priority levels:** `TaskPriority` (`src/types/index.ts`, `"LOW" | "MEDIUM" | "HIGH"`) is real and persisted (`redcheck-backend`'s `Task.priority`, defaults to `MEDIUM`). `src/utils/priorityColors.ts` is a **separate palette from `subjectColors.ts`** on purpose — priority and subject are two different visual dimensions on the same task, and reusing one color system for both would make them visually collide; it also exports `PRIORITY_ORDER` (`HIGH, MEDIUM, LOW`) and `sortTasksByPriority`. `TaskRequest.priority` is optional: omitting it means "default to MEDIUM" on create or "keep the task's current priority" on update (mirrors `redcheck-backend`'s `TaskService`), so call sites that don't care about priority (e.g. `AgendaView.tsx`'s drag-and-drop `rescheduleTask`) can leave it out rather than having to read-then-resend the task's current value.

Priority selectors live in every task create/edit form: the inline "add task"/"edit task" forms (`SubjectSection.tsx`'s `newTask` state, `TaskItem.tsx`/`OverdueSection.tsx`'s shared `updatedTask` state — both lifted in `DashboardPage.tsx`) and `CalendarTaskModal.tsx`'s own local form state. Badges (colored pill, `getPriorityColor(priority).bg/text/dot`) show on `TaskItem`/`OverdueSection` rows; the calendar's Month/Week chips are too small (`text-[8px]`/`text-[9px]`) for a full badge, so priority reads there as a `border-l-2` accent instead using `getPriorityColor(priority).border`, and Day view's fuller cards (`renderDayTaskCard`) and compact hourly chips (`renderCompactHourTask`) get a small priority dot next to the subject name/time. `DashboardPage.tsx` has a "sort by priority" toggle (`sortByPriority` state, next to "Select" in the bulk-actions row) that reorders each subject's `tasks` via `sortTasksByPriority` in a `displaySubjects` memo built on top of `filteredSubjects` — both the Tasks panel and `OverdueSection` read from `displaySubjects`, same as they already shared `filteredSubjects` for search.

**Pending: task tags.** Deliberately deferred, not bundled into priority levels above (the two were originally scoped together, but tags are a distinct feature — free-form/multi-value vs. priority's fixed 3-value enum — and were judged to deserve their own round rather than padding this one). Same backend-first requirement applies: needs a `redcheck-backend` schema change before any frontend work.

**Pending: Google Calendar sync.** Not implemented — two-way sync (or even one-way export) needs an OAuth2 flow against Google's Calendar API, which has to live on `redcheck-backend` (client secret, token storage/refresh, and the actual Calendar API calls can't safely happen from the frontend). Nothing on the frontend depends on this yet, so there's no partial/dead scaffolding to work around when it's built. Once the backend exposes connect/disconnect + sync endpoints, the frontend piece is a Settings-modal toggle (same pattern as `remindersEnabled`/`taskFeedbackEnabled`) that kicks off the OAuth redirect and reflects connection status.

**Confetti on daily completion:** `src/components/Confetti.tsx` — a dependency-free CSS-only burst (no canvas/library), fired from `DashboardPage.tsx` only on the actual transition of `totalPending` from >0 to 0 (tracked via a ref starting at `null`, not `0`, so a fresh load that's already empty never fires it). Follows the same render-phase-update pattern as `ModalOverlay`'s `shouldRender`/`isVisible` (compare two pieces of state during render, not inside a bare `useEffect` body) — the `react-hooks/set-state-in-effect` and `react-hooks/refs` lint rules are strict about this project-wide, so reach for that pattern rather than a ref+effect combo when a component needs to react to a changing prop.

**Task-completion feedback:** `src/utils/feedback.ts` exports `triggerHapticFeedback(duration = 40)` (Vibration API), feature-detected/try-caught so it no-ops (returns `false`) where unsupported (e.g. no Vibration API on iOS Safari — a permanent WebKit limitation, not fixable from here) rather than throwing. A sound effect was tried here too (a Web Audio "ding") and removed after user feedback — don't re-add one without being asked. **Must be called synchronously, before any `await`, directly inside the click handler** — `handleToggleTask` and `handleBulkComplete` both call it as their first line, before the awaited `toggleTask`/`Promise.all`. This isn't a style preference: the Vibration API requires an active user gesture, and that gesture context does not survive crossing an `await` boundary on mobile browsers, so calling it after the awaited API call resolves silently no-ops on phones even though it appears to work fine on desktop (verified via Playwright — vibrate fires ~70ms after the click, well before a deliberately-delayed mock network response).

The 40ms default (was 15ms) exists because a report of "vibration doesn't work" on a real Android device survived cache-clearing, confirming the Settings toggle was on, and confirming the OS-level vibration setting was on — i.e. the gesture-timing fix above wasn't the whole story. `navigator.vibrate()`'s own return value distinguishes two different failure modes that look identical from here: `false`/thrown means the browser rejected the request outright (unsupported, no gesture); `true` with nothing felt likely means the pulse ran but was too short for that phone's motor to physically respond in time — a device-level limit, not a bug in this code. `SettingsModal.tsx` has a "Test vibration" button (200ms, a maximally-deliberate direct click) next to the toggle specifically to tell these apart when this comes up again — check what it reports before assuming another gesture-timing-style bug.

Gated by a Settings-modal toggle (`taskFeedbackEnabled`, `localStorage`, opt-out — defaults on unlike the reminders toggle, which is opt-in) and only fires when a task is marked complete, not un-completed.

**Onboarding tour:** `src/components/OnboardingTour.tsx` — a 4-step dismissible product tour (Welcome / SmartCheck AI / Calendar / Focus Mode+Command Palette), built on `ModalOverlay` like every other modal here. Shown automatically once, on the first successful dashboard load, gated by a `localStorage` flag (`rc_onboarding_seen`, same persisted-flag pattern as `remindersEnabled`/`taskFeedbackEnabled`) set in the initial-data effect in `DashboardPage.tsx`; replayable anytime via the command palette's "Show tour" action (`setShowOnboarding(true)`). Lazy-loaded (`lazy()` + `Suspense`) like the dashboard's other on-demand modals, so it doesn't add to the main dashboard chunk for returning users who'll never see it again.

**User feedback:** `FeedbackModal.tsx` (lazy-loaded, same tier as `SettingsModal`/`CalendarTaskModal`) posts to `redcheck-backend`'s `POST /feedback` (`src/api/feedbackApi.ts`) with a category (`FeedbackCategory` — `BUG`/`SUGGESTION`/`PRAISE`/`OTHER`, picked via 4 chip buttons, not a `<select>`) and a message (2000 char cap, enforced client-side to match the backend's `@Size`). It's write-only — there's no in-app way to view past submissions, by design (this app has no admin UI). Two entry points, deliberately no permanent icon/button added to the dashboard chrome: a row inside `SettingsModal`'s new "Support" section (`onOpenFeedback` prop — `DashboardPage.tsx`'s `handleOpenFeedback` closes Settings before opening Feedback rather than stacking two `ModalOverlay`s), and a Command Palette action (`send-feedback`, same pattern as `show-tour`). `showFeedbackModal` is included in the dashboard's Escape-key skip list alongside `isSettingsOpen`/`isAiModalOpen`/`paletteOpen`, since `ModalOverlay` already handles Escape for it independently.

**Command palette:** `src/components/CommandPalette.tsx`, opened by Ctrl/Cmd+K (superset of the inline dashboard search — same task/subject substring matching, plus a contextual `actions` list built in `DashboardPage.tsx` as a plain array, deliberately not `useMemo`'d since two entries close over functions recreated every render anyway). Built on `ModalOverlay`, so it gets focus-into-the-search-input, Tab trap, and Escape for free. Selecting a task result calls back into `handleOpenTaskEditor`, which reuses the exact deadline-formatting logic `TaskItem`'s own edit button uses. Keyboard nav keeps a highlighted index as state but derives the *clamped* index at render time (`clampedIndex`) rather than syncing it back into state via an effect, for the same lint-rule reason as the confetti component above.

**Empty-state illustrations:** `src/components/illustrations/` — flat, geometric, hand-coded SVGs (not an attempt at detailed scenes, which don't hold up well without a real designer) replacing generic lucide icons in the two places with real dedicated empty-state layout: `EmptyTrayIllustration` (Trash) and `WelcomeIllustration` (Dashboard's zero-subjects first-run state). Both use Tailwind `fill-*`/`stroke-*` classes (not inline `currentColor`) so they pick up dark mode automatically. The Dashboard's inline "no pending tasks today" text (a one-line decoration, not a dedicated empty state) deliberately still uses a plain lucide `Coffee` icon — not every icon needs a custom illustration, just the ones with room to show one.

**Testing:** Vitest (`vite.config.ts`'s `test` block; the file imports `defineConfig` from `vitest/config`, not `vite`, so the same config serves both) + React Testing Library, `environment: 'jsdom'`. `test.globals` is deliberately **off** — every test file imports `describe`/`it`/`expect`/`vi` explicitly from `"vitest"` rather than relying on ambient globals. Because of that, RTL's auto-cleanup-between-tests (which hooks itself to a global `afterEach`) doesn't self-register either — `src/test/setup.ts` calls `cleanup()` in an explicit `afterEach` itself; don't remove that or tests will bleed DOM state into each other. That same setup file also stubs `window.matchMedia` (jsdom doesn't implement it, and `ThemeContext` calls it on init) — any other browser API a test newly depends on that jsdom lacks belongs there too. Tests live next to what they test (`Foo.tsx` → `Foo.test.tsx`), not in a separate `__tests__` tree. A page/component that uses `useTheme`/`useLanguage` needs to be rendered wrapped in `<LanguageProvider><ThemeProvider>` (see `LoginPage.test.tsx`/`AuthFloatingNav.test.tsx` for the pattern); one that calls `useNavigate`/`<Link>` needs `<MemoryRouter>`. Mock API modules per-file with `vi.mock("../api/xxxApi")` rather than letting real network calls hit `axiosConfig`'s real `api` instance.

Login/Register's email/password/username `<input>`s now have `htmlFor`/`id` associating them with their `<label>` (fixed 2026-09-09 — the `LoginPage` test's `container.querySelector` fallback predates this and could be simplified to `getByLabelText` now, just wasn't worth touching a passing test for it). The same missing-association pattern still exists in `TaskItem.tsx`, `SubjectSection.tsx`, `OverdueSection.tsx`, and the new-subject form in `DashboardPage.tsx` — left alone since fixing those wasn't in scope, but worth doing next time any of those forms are touched.

**Shared auth-page chrome:** `src/components/AuthFloatingNav.tsx` is the mobile-row + floating back/language/theme controls used by `LoginPage`, `RegisterPage`, `TermsPage`, and `PrivacyPage` — this used to be ~55 lines of copy-pasted JSX per page (4×). The back action differs per caller (Login links out to `redcheckapp.com` via `backHref`; the other three navigate internally via `onBack`), and the mobile row's own spacing differs too (Login/Register center a card and pass nothing, defaulting to `w-full max-w-md mb-4`; Terms/Privacy are full-width scrollable documents and pass `mobileRowClassName="px-4 pt-4"`) — check both call sites again before assuming one prop set fits all four pages.

**Bundle size:** `framer-motion` (~120KB) was removed — it was used in exactly one place (`PageTransition.tsx`) for a two-property enter animation, and its `exit` prop was dead code (needs `<AnimatePresence>` to do anything, and nothing in the app renders one). If a future animation need seems to call for a library, confirm first that plain CSS transitions (the pattern in `PageTransition.tsx`/`ModalOverlay.tsx`) genuinely can't do it — the bundle cost surfaces immediately in `npm run build`'s chunk-size output. `BackgroundParticles.tsx`'s `@tsparticles/slim` chunk (~145KB) was reviewed and left alone: it's already the lighter of the two tsparticles bundles, it's lazy-loaded behind its own `Suspense` boundary so it never delays the dashboard's initial load, and hand-picking individual tsparticles plugins to shave it further wasn't judged worth the added fragility for a decorative background effect.

**Error monitoring / analytics:** not integrated — no Sentry, PostHog, or similar. The user asked for this to stay documented-but-inactive until an account/DSN is provided, so **don't add a monitoring SDK dependency speculatively**. When one is ready to wire up: `ErrorBoundary.tsx`'s `componentDidCatch` is the natural hook for render-error reporting, and a `window.addEventListener("unhandledrejection", ...)` /`window.onerror` pair (not yet present anywhere) would be needed alongside it to catch errors outside the render tree (e.g. in event handlers, async code). `PrivacyPage.tsx` already has a cookie-usage disclosure section — adding any analytics/monitoring tool that sets cookies or does fingerprinting needs that section updated too, for GDPR consistency with the rest of the app's privacy posture.

**AgendaView (calendar):** `getTasksForDate(subjects, date)` (module-scope, not a closure) filters `subjects` down to tasks due on a given day — this is the live, always-in-sync source, but (like the rest of the dashboard) only ever has *pending or completed-today* tasks, since it's fed by `subjects` (`getSubjectsWithTasks()`, dashboard-scoped). For a **past** date that's not enough (a task completed three days ago has no representation in `subjects` at all), so every call site actually goes through `getMergedTasksForDate(date)` instead of `getTasksForDate` directly: today/future dates still resolve via `getTasksForDate(subjects, date)` unchanged, but a strictly-past date resolves via `getHistoricalTasksForDate(historicalTasks, subjectNameById, date)` — a parallel filter over `historicalTasks`, a flat `TaskResponse[]` fetched from the backend's `GET /tasks?from=&to=` (`getTasksForDateRange` in `taskApi.ts`), which unlike `subjects` includes completed tasks. `isDateInPast(date, today)` (`date < today && date.toDateString() !== today.toDateString()`) is the single past/not-past test shared by all of this.

`historicalRange` (a `useMemo`) computes the from/to bounds actually visible — a single day (Day view), the visible Monday–Sunday (Week view), or the 1st–last day of the displayed month (Month view; adjacent-month cells in the grid are blank, see `calendarCells`, so the range never needs to spill into neighboring months). A `useEffect` keyed on `historicalRange` fetches exactly once per navigation, and **only** when `historicalRange.from` is itself in the past — browsing entirely future dates does zero extra network calls. This range-based, one-call-per-view-change design deliberately avoids per-day fetching (a 42-cell Month view firing 42 requests) the same way `GET /subjects/with-tasks` avoids the dashboard's old per-subject N+1.

Because past-day chips now render real, editable tasks (not just a heatmap count), a create/update/delete/toggle reaching the calendar for a past date needs `historicalTasks` to reflect it immediately, not just after the next navigation re-triggers the effect — `refreshHistory()` bumps a `historyRefreshTick` counter (in the effect's deps) after each of the four mutation paths: `rescheduleTask` (drag-and-drop), `renderCompleteToggle`'s click handler, and `CalendarTaskModal`'s `onCreate`/`onUpdate`/`onDelete` (wrapped as `handle*TaskFromCalendar` specifically to add this, since the modal is otherwise handed the raw `DashboardPage` callbacks directly). If a 5th mutation path is ever added here, wire it the same way rather than assuming `subjects`-driven re-render is enough.

The heatmap (`getProgressHeatmap()`) fallback badge (`completed/total` count) still exists but now only fires when `getMergedTasksForDate` returns zero rows for a past day with a nonzero heatmap count — e.g. a day whose only task was later hard-deleted. It's no longer the primary way past days are shown.

Subject color coding: `getSubjectColor(subjectId)` (`SUBJECT_COLOR_PALETTE`, 8 Tailwind color families, keyed by `subjectId % length`) gives every pending task a stable color regardless of array order/filtering — used by Day view's two task-card renderers, Week view's day-cell chips, and Month view's day-cell chips. Completed tasks always render gray/muted instead, ignoring subject color. Month view shows up to 2 truncated task-title chips per cell (`+N {t.moreTasks}` beyond that) — same visual pattern as Week view's chips (which show up to 4), reused rather than re-invented.

Jump-to-date: a `CalendarDays` icon button folded into the existing prev/Today/next pill (not a separate boxed control) opens a hidden native `<input type="date">` via `showPicker()` (falling back to `.click()` if unsupported), and its `onChange` calls `setCurrentDate` directly — cheap and accessible compared to hand-rolling a date-picker popover. The header row (`AgendaView.tsx`'s `--- HEADER ---` section) runs at the edge of its available width once the calendar column shrinks (fixed-width sidebar + fixed-width right panel on desktop), so that row needs `flex-wrap` — without it, extra header content (like this button) silently overflows past the panel edge instead of wrapping to a second line.

Day view places tasks on the hourly grid (`timedTasksByHour`, keys clamped to `DAY_VIEW_HOUR_START`–`DAY_VIEW_HOUR_END`) instead of floating an unrelated list over it, plus an `allDayTasks` strip above the grid for deadlines with no time component. Two things matter if this is touched again:
- **The hour-label column and the grid+tasks column must share one `overflow-y-auto` scroll container, never two independent ones.** They did originally (each column scrolled on its own) and it was invisible because the old task list wasn't tied to specific hours; the moment tasks became hour-row-aligned, any drift between two independently-scrolling siblings became visibly broken misalignment.
- **Each hour row needs `shrink-0`.** Without it, flexbox lets 80px (`h-20`) rows compress below that height when the column's total content (13 hours) exceeds the visible area — rows with a task resist shrinking below their content's min-height while empty rows compress freely, drifting the whole grid out of alignment. `renderCompactHourTask` (single-line, for the grid) is deliberately more compact than `renderDayTaskCard` (the fuller card, used only in the all-day strip which isn't height-constrained) — the fuller card doesn't fit two of itself inside one fixed 80px row even with an overflow fallback, which is what motivated having two card variants instead of one.
- The red "now" line's `top` (in `AgendaView.tsx`) is a hand-computed `rem` offset assuming exactly 80px/hour — if the hour range or row height ever changes, update that formula too.

Create/reschedule from the calendar: `CalendarTaskModal.tsx` is a single modal (built on `ModalOverlay`, like the app's other modals) that handles both creating a new task (a "+" affordance on hover in Month/Week cells and Day-view hour rows, plus an "Add task" button in Day view's empty-day state) and editing/rescheduling an existing one (clicking any task chip/card in Day/Week/Month). AgendaView owns a single `taskModalState` (`{mode:"create", date, defaultSubjectId} | {mode:"edit", task} | null`) and passes `onCreateTask`/`onUpdateTask`/`onDeleteTask` callbacks down from `DashboardPage.tsx` (`handleCalendarCreateTask` etc.), which call the same `taskApi.ts` functions as the existing inline per-subject forms and update the same `subjects` state — so a change made from the calendar shows up in the Tasks panel immediately and vice versa. This modal is deliberately self-contained (not just reusing the Tasks panel's inline edit form) because the Tasks panel isn't on screen at the same time as the calendar on mobile (separate bottom-nav tabs) — the calendar's create/reschedule flow has to work standalone. Every task-chip/cell click that opens this modal calls `e.stopPropagation()` first, since the same click target's parent cell already has its own `onClick` (navigate to Day view for that date).
